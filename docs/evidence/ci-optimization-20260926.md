# Blacksmith CI optimization audit — 2026-09-26

Scope: baseline source `978da0a9cd87ff387d0d0b519fd65f100987d40f` and the optimization branch through `4be0395`, using the completed [Blacksmith run 36282904405](https://github.com/BeamoTech/beamo-wipe/actions/runs/36282904405) as the baseline and the authorized [candidate run 36290999266](https://github.com/BeamoTech/beamo-wipe/actions/runs/36290999266) as a trial. The timestamped baseline Linux log puts checkout at 2.4 seconds, KVM preflight at 0.3 seconds, actionlint at 1.2 seconds, cache restore at 0.3 seconds, evidence preparation at 0.1 seconds, and artifact upload at 1.4 seconds. Together these are under six seconds. Further setup-step changes would have negligible cost effect compared with the 278-second source phase, 193-second ISO phase, and 581-second QEMU phase. The candidate's source phase took 280 seconds and ISO phase took 193 seconds; these single-run observations show no meaningful elapsed-time saving in those phases.

The QEMU phase is the largest serial cost. The timestamped baseline job log shows about 43 seconds from the QEMU step start to its verification command, mostly container setup and dependency installation; the USB image then built in about 6.6 seconds. The trial reached its verification command in about 8.6 seconds and built the USB image in about 7.5 seconds. That single observation is consistent with cheaper QEMU container setup, but cache warmth and runner variation are uncontrolled, so the package-specific saving is unproven. Baseline verification spent about 62 seconds on six real-nwipe host boundaries, 313 seconds on six BIOS wipe-and-report journeys, and 145 seconds on the remaining UEFI, USB, speech, and Secure Boot probes. Each journey has a distinct safety or compatibility assertion. The current QEMU script shares loop-device ownership, mount state, process IDs, and cleanup traps, so parallelizing its guests without isolating those resources could invalidate the safety evidence. We did not remove any of those checks.

The [Blacksmith runner catalog](https://docs.blacksmith.sh/blacksmith-runners/overview) lists a 4 vCPU x64 Ubuntu runner with 16 GB memory and 80 GB storage and states that x64 Linux supports nested KVM. Blacksmith says free-minute consumption scales with vCPU count. Relative to the 8 vCPU baseline, the smaller runner reduces equivalent 2 vCPU minutes if its Linux job completes in less than 2,128 seconds (35:28). At the published 2 vCPU Ubuntu rate of $0.004/minute, the baseline is approximately $0.284 in runner compute before free minutes or account-specific terms; the 4 vCPU job would be approximately $0.142 if it took the same 1,064 seconds. This is a calculation from [public pricing](https://www.blacksmith.sh/pricing), not a measured bill. A completed 4 vCPU elapsed time, peak disk use, and account-specific price remain unmeasured. It may be slower, especially while the five source containers share four cores; the Orca test also retains its 300-second timeout.

[Blacksmith's metrics for the baseline Linux job](https://app.blacksmith.sh/BeamoTech/runs/36282904405/jobs/108518053070?tab=metrics) show 2,456 MB peak memory and CPU usage at P50 12%, P90 22%, P95 57%, and P99 99% of its 8 vCPUs. Memory fits in the 4 vCPU runner's 16 GB allocation. CPU peaks show why the runner change remains a trial: some source work can become slower even though most samples use less than four cores. The candidate ran its source and ISO phases on 4 vCPUs, but its QEMU failure prevents a completed-job cost comparison.

Prepared changes in the local candidate commits:

- Try the 4 vCPU Linux runner. The native 2 vCPU Windows job and required `CI gate` stay in place.
- Update actionlint's allowed runner label for that trial.
- Fetch only the triggering commit for the Linux checkout. The gate uses `git rev-parse HEAD` and `git status` for provenance, not history or tags; the baseline checkout took three seconds, so any saving here is minor.
- Remove the migration-only automatic trigger for `codex/ci-*` pushes. PRs and main retain the full gate; manual dispatch remains available for exact-source branch verification. PR runs still cancel superseded PR runs, while main and manual runs remain uncancelled.
- Permit fallback to an older trusted pip download cache when the CI script changes. Only a successful main push may save a cache; no test result, launcher, ISO, or USB image is reused.
- Skip Linux cross-compilation of the Windows test binary on Blacksmith: the independent native Windows job compiles and runs the same suite, and the Linux bundle builder still compiles the shipped Windows launcher. Standalone and legacy callers keep the cross-compile check.
- Trialed 0.25-second QEMU serial-marker, report-completion, and key-release polling in `4be0395`. The baseline log contained 85 "reached new marker" and 40 "reached marker" events; 48 of 85 consecutive same-guest marker intervals were 0.9–1.1 seconds. That motivated the trial, but the candidate run failed during guest key-release synchronization. The shortened polling and its seven mocked-poll tests were removed after the run. Exact-marker checks, mandatory guest release acknowledgment, timeout handling, and release retries remain. The run does not isolate the polling change as the cause; reverting an unproven synchronization optimization is the conservative response.
- Read Orca's growing debug log from a byte checkpoint for each speech assertion instead of reopening and decoding all earlier screens on every 20 ms poll. The live Orca/AT-SPI events, focus nudges, 300-second parent bound, and exact announcements remain required. A local helper check covered absent logs, UTF-8 byte offsets, fresh speech, and focus events. In a local 5.5 MiB synthetic log, 80 polls took 0.241 seconds with the previous full-file read and 0.001 seconds with bounded reads; only hosted Orca can establish a CI runtime saving.
- Exclude ignored pip, test, type-check, Ruff, virtualenv, and generated preview caches from the private ISO source copy. Also omit the repository's historical `docs/`, `tests/`, and `developer_tests/` trees: they run or document separate source gates, while the ISO builder consumes already staged live assets and the selected source trees in `live_build_inputs()`. With the same local checkout, rsync dry-runs selected 134,771,233 bytes using the original excludes, 123,160,391 bytes after the disposable-cache excludes, and 17,788,453 bytes with the non-build trees omitted. A real local copy retained the staged `START-HERE.html` asset and produced an identical `live_build_inputs()` digest. These are local copy-size measurements, not hosted runtime savings; actual cache bytes copied in the baseline were not measured.
- Remove compiler, Autotools, pkg-config, and development headers from the QEMU verification container. The pinned nwipe binary is compiled in the ISO chroot; the verifier executes that extracted binary using the same three Debian runtime library packages explicitly installed in the shipped image. Baseline QEMU-container setup before verification took about 43 seconds, but its portion attributable to the removed packages is unmeasured.
- Remove the QEMU verification container's explicit `file` and `kmod` installs. Neither the USB builder nor `qemu-verify.sh` calls `file` or `modprobe`; the worker's `check-ci-kvm.sh` loads and probes the required kernel modules before Docker starts the privileged verifier. Keep `hdparm`: the extracted nwipe binary requires it even for the disposable host-method checks. The package removal has no measured runtime saving yet.
- Omit Git from the outer ISO builder container. The outer script uses rsync, Python, and live-build; the nwipe hook installs Git independently in the image chroot, then purges it. [Debian's Bookworm live-build package](https://packages.debian.org/bookworm/live-build) does not require Git. The baseline outer setup downloaded 7,264 kB for Git and 2,053 kB for git-man, before their dependencies; actual elapsed-time savings are unmeasured. Keep the other recommended bootstrap packages until an exact-image qualification can prove that fewer dependencies preserve signed debootstrap and secure boot output.
- Install the three pinned Python test packages in one pip invocation rather than starting pip's resolver twice before the real Orca gate. Package pins and browser install remain identical. This removes duplicate setup work, but its elapsed-time saving is unmeasured.
- Skip the second `apt-get update` when the hosted desktop wrapper has just refreshed package lists in the same container. Standalone `ci-desktop.sh` still refreshes before installing. The desktop gate ended before Orca in the baseline, so this removes duplicate metadata work without a measured critical-path saving.

This pass found no evidence that dropping a format, lint, type, accessibility, negative safety, native Windows, ISO, vulnerability, QEMU, or provenance check would be safe. Blacksmith's existing Docker image cache already operates automatically. Caching the roughly eight-second Chromium download would introduce a much larger browser archive for a small possible saving, so it is not part of this change.

The baseline Linux evidence artifact upload was 223,470 bytes and completed in about 1.3 seconds. Shortening its seven-day retention or omitting logs has little measured runtime upside and would make the verification harder to diagnose, so the artifact policy stays unchanged.

The source phase's long tail is the real Orca screen-reader test: it started after dependency setup at 00:35:36 and the tests phase ended at 00:39:26 in the baseline log. Its waits observe live AT-SPI speech/focus events across result and warning screens; cutting those waits or replacing Orca with a mock would remove the native accessibility evidence. The other four source gates had completed before the tests phase ended, so rearranging their execution does not currently shorten the critical path. Bounded log reads reduce repeated file work without changing those waits.

Other reviewed options remain unchanged. The preview JavaScript syntax test runs in the full Python suite, but the separate preview gate also proves that a malformed generated script fails its own receipt; its focused regression depends on that independent check. The aggregate check is needed to preserve the single required status while enforcing both Linux and Windows results. Skipping QEMU for PRs or selected paths would weaken the current full-image gate. Parallel guest execution needs separate evidence that UI events, private mounts, loop ownership, and fail-closed cleanup remain correct; a speculative change to those boundaries is not included here. The failed candidate run shows why local mocked polls were insufficient to accept shorter guest synchronization.

A final source-container package audit found active tests for the seemingly duplicate tools: the Python suite executes ShellCheck against the kiosk script, Node against generated browser flows, xorriso against an ISO inspection fixture, FAT/mtools against USB image readback, rsync against live-source copy behavior, and Git against provenance/checkout fixtures. Removing those packages would silently skip tests or turn a meaningful check into a fixture-only check. The duplicate desktop metadata refresh was removed. The explicit `python3-setuptools` entries also remain: Bookworm's [python3-pip package](https://packages.debian.org/bookworm/python3-pip) depends on setuptools, so deleting those lines would not remove a package. No further package or gate removal is supported by the current evidence.

The remaining fixed QEMU sleeps serve distinct boundaries: 0.4 seconds between unacknowledged key taps, six seconds for the owner last-chance countdown, five seconds after report-USB hotplug, and one second between speech-menu hotkey retries. Those are not marker polling delays and were left intact.

The second host and BIOS journey for each method is also intentional. The release evidence inventory requires separate files for both runs, and the [2026-09-12 qualification history](../production-completion-2026-09-12.md) records a Three-overwrites failure after both Everyday journeys had passed. Removing repeats would save roughly 31 seconds of host checks plus 156 seconds of BIOS checks in the baseline, but would remove real repeated-session evidence and change the release contract. The current optimization keeps all six runs of each type.
